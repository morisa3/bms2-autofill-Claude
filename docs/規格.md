# 新版規格（討論確認紀錄）

本文件記錄與使用者討論後確認的決策，作為新版開發依據。尚未確認的項目列於最後「待確認」。

## 1. 技術方向

| 項目 | 決定 |
|---|---|
| 語言 | Python |
| 介面 | PySide6（不用 Flet：網站內嵌、大量表格、意見文字編輯都需要 Qt） |
| 瀏覽器 | 以 QtWebEngine 內嵌 bms2 網站；需先實測登入（見第 6 節），不通過則保留外部 Chrome |
| 改版方式 | 方案 ③：新專案，從 Systemautofill v1.00 搬入純邏輯模組及其測試；介面、瀏覽器、流程重寫。舊版 v1.00 照常使用至新版功能跟上 |
| 資料來源 | 以線上唯讀掃描為主（基本資料、前期、本期）；Word 只當備援 |
| 資料鎖定 | 本期一律以網站劣化 ID 鎖定，不依 Word 或網頁順序 |

## 2. 操作版型

採 **A 當外框，右側面板切換 B／C**：

- **A 外框**：左側內嵌網站（前期／本期可分頁或並排，前期可隱藏），右側助手面板。螢幕寬度小於 1600px 時網頁區改為分頁、不並排。
- **B 逐筆審查**：一次一筆，只列異常與需確認項目。
- **C 總表**：一列一組配對（構件、位置、前期備註、本期備註、判定、信心），雙擊展開為 B 的編輯卡；也用於核對下包資料。
- 流程收成三步：**掃描 → 審查 → 填寫**。

## 3. 網站結構（依使用者提供的 XPath 與網頁原始檔）

- 缺失主頁面各構件表以 table id 定位（`approach_bank`、`abutment`… 見 `bridgefill/core/config.py` 的 `COMPONENTS`）。
- **不得寫死欄位或列號**：有無「狀態」欄會讓欄位整欄右移；應讀表頭文字找「詳細資料」「DERU」「維修狀態」欄，再逐列讀取。
- XPath 文件更正：
  - 引道路堤（有狀態欄）橋尾 DERU 應為 `//*[@id="approach_bank"]/tbody/tr[3]/td[6]`（原文件誤植為 tr[2]）。
  - 鋼纜錨碇裝置（橋塔端）`tr[21]` 只是範例橋梁中唯一有缺失的那列（TA20-L），不是固定位置。
- 鋼纜（吊索）與鋼纜保護套管共用 `stay_cable`，以區段標題 span 區分。
- DERU 顯示：
  - `_ 0 _ _`：E＝0（無法檢測），D 留空，無劣化 ID。
  - D＝1：良好，無劣化 ID。
  - 完整數值（例 `3 1 3 3`）：有缺失，需讀第一級頁面。
- 維修狀態欄有三種值：**已維修**、**部分未維修**、**未維修**。
- 「詳細資料(n)」的 n 為第一級頁面的筆數。D＝1／E＝0 的列固定顯示 (1)，那 1 筆是照片紀錄，不是缺失。
- 編號保留左右側（如 `TA01-L`），位置正規化不得刪除 `-L`／`-R`。
- 基本資料：`#width_min`、`#width_max`、`#distribution`（例 `25+1@42.5+2@40+4@40+4@40+30` 表示 S1～S13 跨距，`n@L` 為 n 孔各長 L）。

## 4. 掃描與核對

- 前期：唯讀掃描，不需保存 ID，必須讀取維修狀態。
- 本期：掃描並保存每筆劣化 ID。
- 筆數核對（每一列）：
  - 網站 n ＝ 讀到筆數 → 正常
  - 讀到少於 n → 提示漏讀，重掃該列
  - 讀到重複 ID → 提示重複
  - D＝1／E＝0 的列：n＝1 視為正常，不算缺失
- 漏填檢查（核對下包資料）：

| 階段 | 欄位 | 程式行為 |
|---|---|---|
| 現場必填 | 劣化類型、DERU | 網站本身強制，不另外檢查 |
| 辦公室補齊 | 損壞位置、維修工法、數量、單位、單價、備註（含完整尺寸） | 任一空白或備註尺寸不完整即列為漏填 |
| 不檢查 | 劣化範圍（長、寬、高）、損壞原因 | 忽略（尺寸統一寫在備註） |

## 5. 配對

- 只在「同構件＋同位置列」內找候選，全域一對一配對。
- 判定分類：沿用、範圍加大、單位數量變更、新增、已維修（前期已維修、本期無）、**疑似漏建**（前期未維修或部分未維修、本期無）。
- 現場可能只填劣化類型與 DERU：
  - 同一列只有一筆同類型前期 → 直接鎖定，帶入前期工法、數量、單位、單價、備註。
  - 同一列有多筆同類型前期 → 列為需確認；掃描時先標出這些列，提醒現場在備註寫可區分的短詞（如 `A2-L`）。
- DERU 只作輔助線索，不單獨決定配對。
- 2.1（劣化類型判斷不同但同一筆）需「劣化類型等價表」，由使用者提供。
- 備註自動產生：

| 單位 | 備註尺寸 |
|---|---|
| m | `(m)*1` |
| m（裂縫） | `(mm*m)*1`；寬度大於 10mm 轉為 `(cm*m)*1` |
| m² | `(m*m)*1`，後方的 m 為長度 |
| m³ | `(m*m*m)*1` |

- 引道路堤缺尺寸時以「最小淨寬 × 5m」補，例：淨寬 8m → `A1 AC剝離。(8m*5m)`。

## 6. 登入

- 登入頁使用 Google reCAPTCHA v2（勾選框），另有「使用驗證碼登入」（圖片驗證碼）。
- 使用者在內嵌視窗中**手動**輸入帳密並完成驗證；程式不碰帳密、不碰驗證。
- 內嵌瀏覽器以獨立設定檔保存 Cookie。
- 若 reCAPTCHA 在內嵌環境常跳圖片題，可改用「使用驗證碼登入」。

## 7. 檢測員意見

### U 值與建議文字

| U | 建議 |
|---|---|
| 2 | 持續追蹤，或三年內派工修復（判斷見下） |
| 3 | 一年內派工修復 |
| 4 | 需緊急處置 |

U＝2 的判斷標準是「是否影響橋梁安全或行車安全」：

1. **橋面上的缺失**：影響行車安全 → 三年內派工修復。
2. **下部結構**：先看是否為主構件，再看劣化面積。
   - 面積大 → 三年內派工修復。
   - 面積小 → 持續追蹤。單位為「處」一般即為小面積。
   - 混凝土剝落、沖蝕、小破裂的維修優先級低於混凝土剝落鋼筋外露；小面積且 U＝2 時，常不寫入意見。
3. 系統會追蹤 U 值突然下降的構件；與前期相符的劣化，一般不調整 U 值。新版配對成功時預設沿用前期 U，本期 U 低於前期要提示。

### 由竹子坑橋（程式原稿 vs 最終版）歸納的修正規則

1. 選項要先選定：`建議採【加高／重作】` → 生成前讓使用者選。
2. 基礎裸露要加深度判斷：自動計算裸露深度占基礎深度的比例（1/5、1/3）；基礎深度與治理計畫等本橋特有文字從**前期意見沿用**。
3. 位置只寫到主構件：去掉細部位置（`A1-下游` → `A1`），主梁、橫隔梁編號換成跨號（`1G1-0,13,26` → `S1`）。
4. 構件名稱用實際名稱：斜線構件取實際那一個（`翼牆／擋土牆` → `擋土牆`）；樣態已含名稱就不重複；`其他`、`整體-` 刪除。
5. 相同樣態、相同建議的條目合併（`S1~S3主梁、橋面板混凝土剝落鋼筋外露`）。
6. 不重要的樣態不寫入意見（例：伸縮縫漏水、基礎混凝土剝落、蜂窩、AC 剝離），以 Excel「意見範本」工作表的排除清單管理。
7. 第 1 條已敘明基礎裸露時，刪除後面重複的「橋墩基礎裸露」條目（龍門大橋第 16 條同理）。

### 淨高

- 格式：單跨 `H=[]m`；多跨 `P1=[]m,P2=[]m,...`。
- 本期有新值則保留；沒有則沿用前期意見中的值。
- 意見要針對哪些構件，生成前先勾選。

## 8. Excel 劣化表單

保留原有 7 欄（劣化類型、劣化樣態、維修工法、維修單位、單價、備註、劣化ID），新增欄位與工作表，把目前寫死在程式或寫在「備註」自然語言中的規則改為結構化：

- 新增欄位：同義關鍵字、排除關鍵字、條件欄位／運算／數值、優先序、備註範本。
- 新增工作表：劣化類型等價群組、位置代碼對照、檢測員意見範本（含排除清單）。
- 提供轉換程式，把 1111v1 自動轉成新格式。
